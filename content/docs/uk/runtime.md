# Runtime

`clause_runtime` — це бібліотека на C++23 без LLVM. Вона володіє контекстами,
купами процесів, атомами, завантаженими модулями й обліком життєвого циклу та
виконує процеси Erlang на робочих потоках планувальника
([процеси](processes.md)). Усі API внутрішні для проєкту; виклики з боку хоста
мають бути серіалізовані для кожного runtime й не перекриватися з виконанням
програми, чиї робочі потоки синхронізуються між собою ([потоки](#threads)).

## Компонування

Скомпонуйте рівно один runtime, зібраний для цілі, через
`Clause::generated_program`:

```cmake
add_executable(harness harness.cpp)
target_link_libraries(harness PRIVATE Clause::generated_program)
```

Він приносить архів, заголовки ABI/runtime і C++23, але не LLVM.
[link_consumer.cpp](../tests/runtime/link_consumer.cpp) показує повний
життєвий цикл.

## Життєвий цикл

[runtime.hpp](../runtime/include/clause/runtime/runtime.hpp):

- `Runtime::start(options)` → `std::expected<std::unique_ptr<Runtime>, Status>`.
  Типові значення: поточна версія ABI й нативна ширина терма, `max_atoms` 2^20
  (щонайбільше 2^26; програми задають його через `--max-atoms`,
  [опції runtime](executables.md#runtime-options)). Кількість контекстів не
  обмежена. `process_heap` і `process_stack` — це опції контекстів, створених
  через `create_context()`; `memory_limit_bytes` — необов'язкове
  [обмеження на весь runtime](runtime-heap.md#runtime-memory-limit), про яке
  звітує `memory_bytes()`. Типово жодне з них не обмежене.
- `create_context()` або `create_context(heap_options, stack_options)` →
  позичений `ProcessContext*`, стабільний до знищення. Типові значення купи:
  мінімальна купа в 233 слова (`min_heap_words`) і без обмеження пам'яті
  (`limit_bytes` = `UNLIMITED_HEAP_BYTES`; заданий бюджет — це кратне слову
  значення, щонайменше мінімальна купа). Стек теж не обмежений, якщо не задано
  `StackOptions::limit_words`.
- `destroy_context(ctx)`, `shutdown()`: shutdown повертає `busy`, поки
  лишаються контексти; після цього він ідемпотентно успішний, а пізніші
  виклики повертають `stopped`. Деструктор прибирає контексти, що лишилися.
- Ідентичності контекстів і runtime не використовуються повторно; їх
  вичерпання дає збій. Ідентичність контексту містить його номер pid
  ([pid](terms.md#pids-and-references)). Вказівник на контекст — це позика, а
  не ідентичність. `lifetime()` дає слабкий токен, що повідомляє
  `alive() == false` до демонтажу купи.
- Виклики життєвого циклу ніколи не кидають винятків і нічого не виводять.
  Значення статусу: [abi.md](abi.md#runtime-services).

Порядок завершення: закрити записи планувальника → знищити контексти →
звільнити реєстрації коду → знищити сервіс планувальника → таблицю атомів
останньою. Дескриптори розв’язаних функцій утримують код після завершення
runtime, але слова їхніх слотів атомів не утримують написання. Сховище атомів
виводить глобальні слоти з ужитку до звільнення записів; доступ до написання
через збережений Term нефіксованого атома повертає `expired_context`.

## Пам'ять процесу

Кожен контекст володіє одним `ProcessHeap`
([process_heap.hpp](../runtime/include/process_heap.hpp)); його розкладку,
ділянки, розміри, допуск, корені й збирання описано в
[runtime-heap.md](runtime-heap.md). API хоста:

- `allocate(words)` повертає обнулене сховище слів. `reserve` дає резервацію
  лише з переміщенням (move-only) з явним підтвердженням і автоматичним
  відкотом. Одна резервація за раз на купу: спершу будуйте дочірні елементи,
  батьківський резервуйте останнім. Сирі слова `allocate()` мають лишатися
  нулями або містити повні об'єкти
  ([розкладка слів](runtime-heap.md#word-layout)).
- Нуль, переповнення й вичерпаний бюджет відхиляються до публікації:
  `out_of_memory` (виділення) або `limit_exceeded` (бюджет); згенерований код
  отримує точний статус
  ([поведінка під час збоїв](runtime-heap.md#failure-behavior)).
- `add(value)`/`copy_to` копіюють граф іншого процесу того самого runtime
  ([копіювання між купами](runtime-heap.md#copying-between-heaps)).
- `used_words` рахує виділені слова, `capacity_words` — блок купи й
  фрагменти, `off_heap_words` — буфери поза купою, на які посилається цей
  процес, кожен один раз ([розміри й бюджет](runtime-heap.md#sizing-and-budget)).
- `verify()` обходить блок купи й кожен фрагмент і перевіряє, що кожен слот
  терма вказує на початок об'єкта того самого процесу (тести й налагодження;
  інакше `corrupt_heap`).
- `collect(roots)` копіює все досяжне з коренів процесу й кореневих слів хоста
  в новий блок купи ([збирання](runtime-heap.md#collection)). Виконується лише
  в точці безпеки, інакше `unsafe_point`
  ([корені й точки безпеки](runtime-heap.md#roots-and-safe-points)); згенерований
  код збирає у власних точках безпеки
  ([збирання у згенерованому коді](runtime-heap.md#collection-in-generated-code)).
  Хостові Term — однослівні значення без коренів; після збирання їх слід
  відновлювати з переписаних коренів. Вони не мають перевірок часу життя чи
  застарілості, і їх не можна читати після збирання або завершення процесу.
  Фабрики й резервування зберігають власні токени часу життя й надалі
  повідомляють `expired_context`.

## Сервер коду й вбудовані функції

Кожен runtime володіє одним `CodeServer`
([code_server.hpp](../runtime/include/clause/runtime/code_server.hpp),
[callable.hpp](../runtime/include/clause/runtime/callable.hpp)):

```cpp
auto functions = std::make_unique<ModuleRegistry>();
auto added = functions->add("identity", 1,
    [](ProcessContext &, std::span<const Term> args) -> CallResult<Term> { return args.front(); });
auto loaded = context.code_server().load({"native_demo", CodeImage::linked(), std::move(functions)});
auto fn = context.code_server().resolve({.module = "native_demo", .function = "identity", .arity = 1});
```

- `ModuleRegistry` відображає точні ім'я/арність (≤ 255) на один викликуваний
  об'єкт, що працює лише з `Term`. `load` заморожує й публікує його; дублікати
  чи збої нічого не публікують.
- Реєстрація також індексує прив'язки згенерованих модулів у хеш-таблицях:
  дескриптори модулів, record і fun — до їхніх прив'язок і визначень, а слова
  атомів `Module:Function/Arity` — до фреймів експорту. Тому динамічні
  виклики, `apply/3`, `fun M:F/A` під час виконання й пошук дескрипторів
  займають сталий очікуваний час щодо кількості модулів і експортів. Індекси
  будуються всередині реєстрації: відхилений модуль не додає записів, і вони
  змінюються лише під ексклюзивним блокуванням сервера.
- `resolve` розрізняє відсутній модуль і відсутній експорт.
  `ResolvedFunction` закріплює образ модуля; `call` перевіряє арність,
  аргументи й результати та перетворює винятки хоста на збої.
- Нативні тіла мають бути синхронними, неблокувальними й не повинні утримувати
  контекст чи span аргументів.
- Обмежений каталог відомих відкладених BIF (`self/0`, `length/1`, `spawn/3`,
  `spawn_link/3`, `send/2`, `make_ref/0`, `garbage_collect/0`, `apply/3`
  (згенерований код натомість викликає `apply/2,3` через служби динамічних
  викликів, [fun](funs.md#dynamic-calls)), `tuple_size/1`, `+/2`) повідомляє
  `not_implemented`; інші незареєстровані імена мовчки повертають
  `unknown_builtin`. Цей шлях хоста не доходить до робочих вбудованих функцій.
- Робочі вбудовані функції живуть у `BuiltinRegistry` сервера й реєструються
  під час запуску runtime; згенерований код, динамічні виклики й fun доходять
  до них через [міст вбудованих функцій](builtins.md).
- `CodeServer::export_frame` знаходить `FrameDescriptor` експорту за модулем,
  атомом функції й арністю; `function_frame` додає вбудовані функції для
  динамічних викликів; `external_fun` інтернує визначення зовнішніх fun,
  побудованих під час виконання.
- Модулі ніколи не вивантажуються; `CodeServer::unload` відкладено, динамічне
  завантаження не підтримується.

## Постійні терми

Одна таблиця на runtime (`memory/persistent_terms`), яка належить
`Runtime::Impl` і доступна через `ProcessContext::persistent_terms()`,
зберігає терми `persistent_term`
([вбудовані функції](builtins.md#persistent-terms)).

- Кожен ключ і значення копіюються у власну область діапазону persistent terms
  runtime (`memory/persistent_region`): одне резервування адрес (64 GiB
  адресного простору на 64-бітних хостах, 256 MiB на 32-бітних), сторінки якого
  виділяються під час виділення областей, тож належність слова до persistent
  terms визначається одним порівнянням діапазону. Копії спільно використовують
  лише літерали модулів, тому кожна область незалежна; її binary спільно
  використовують свої буфери.
- Записи — кореневі слова, які знаходять за хешем ключа (вбудовані функції
  використовують хеш терма `phash2`) і точною рівністю, порівнюючи на місці.
- Читання повертає збережене слово на місці, як літеральні persistent terms
  OTP: будь-який процес може зберігати й надсилати його (копіювання до іншого
  процесу зберігає слово); збирання не змінює його, а допуск приймає як літерал.
  Буфери повідомлень і нові persistent terms копіюють слова persistent terms.
- **Звільнення пам’яті.** Область заміненого чи видаленого значення виводиться
  з ужитку під новою епохою. Відтоді кожна копія копіює її слова, а кожен
  процес, зареєстрований на той момент, копіює збережені об’єкти цієї області
  у власну купу під час евакуаційного повного збирання (`Copier` з регіоном,
  кожен об’єкт один раз, буфери binary утримуються до збирання): активний або
  поставлений у чергу процес — на початку наступного кванта, призупинений —
  одразу, через put або erase, що вивели область з ужитку
  (`Executor::evacuate_parked`, під блокуванням виконавця). Коли всі такі
  процеси зроблять це або завершаться, область звільняється. `info/0` рахує
  лише поточні записи.
- Спільне блокування обслуговує читачів на довільній кількості робочих потоків;
  put і erase беруть його виключно (копії створюються до цього). CTest
  `runtime_persistent_terms` перевіряє значення, що переживають записувача,
  читання на місці між збираннями й процесами, замінені та видалені значення,
  які утримують читачі, одночасних читачів і записувачів та звільнення пам’яті
  (копії областей, що виводяться з ужитку, евакуацію, звільнені області й
  облік пам’яті).

## Облік планувальника

`SchedulerService`
([scheduler.hpp](../runtime/include/clause/runtime/scheduler.hpp)) — це запис
життєвого циклу процесів для хоста; він не виконує коду. Програми виконуються
на виконавці ([процеси](processes.md#executor)), який його не використовує.

- `register_process(context)` один раз на контекст (того самого runtime);
  дублікати повертають `already_registered`. `remove_process(id)` прибирає
  запис, що не виконується.
- `begin_dispatch` → running; `finish_dispatch` → runnable, waiting або exited
  (з причиною). `set_suspended` перемикає прапорець на записах
  runnable/waiting. Інші переходи повертають `invalid_transition`.
- `request_shutdown()` закриває реєстрацію, диспетчеризацію й керування
  призупиненням; інспекція й повернення лишаються доступними для спорожнення.
- `run` і `execute` повідомляють `not_implemented`.

## Потоки

Робочі потоки планувальника ([робочі потоки](processes.md#workers)) виконують
процеси на кількох потоках одного runtime. Служби, які вони ділять,
синхронізовано; усе інше лишається в межах потоку, що виконує свій процес, або
захищене м'ютексом виконавця.

- Атоми: `AtomStorage` захищає map написань і власні записи спільним м’ютексом.
  `existing` і `size` використовують спільне блокування; `intern` спершу шукає
  під спільним блокуванням, потім для нового написання бере виключне й перевіряє
  ще раз, тож конкурентні виклики отримують одне слово. Публікація використовує
  загальнопроцесну `detail::atom_table`; допуск і читання написань — її
  неблокувальний індекс за номером (`lookup` також перевіряє власника запису).
  Фіксовані атоми не потребують блокування. Записи не змінюються, доки під час
  завершення їхні слоти не буде виведено з ужитку ([атоми](terms.md#atoms)).
- Код: `CodeServer` захищає свої модулі й визначення зовнішніх fun спільним
  м'ютексом. Пошуки (`find_module`, `resolve`, `atom_word`,
  `record_definition`, `fun_definition`, `export_frame`, `function_frame`,
  `owns`) беруть його спільно; `load` і побудова нового визначення зовнішнього
  fun беруть його ексклюзивно, тож одночасні реєстрації одного імені
  публікують один модуль (інші отримують `duplicate_module`), а змагальні
  виклики `external_fun` отримують одне визначення. Реєстр вбудованих функцій
  заповнюється під час запуску runtime, до виконання будь-якого робочого
  потоку, і після цього лише читається.
- Утримання: модулі ніколи не видаляються протягом життя runtime, а сервер
  знищується після всіх контекстів, тому повернуті ним визначення, фрейми й
  слоти атомів залишаються чинними для кожного виклику та комірки fun.
  Дескриптори `ResolvedFunction` і `find_module` також утримують свій модуль
  після завершення runtime; їхні слоти атомів зберігають слова, а не утримують
  написання.
- Номери pid і портів: `IdentityNumbers` видає номери під ексклюзивним
  блокуванням і допускає слова pid і портів під спільним.
- Пам'ять: облік на весь runtime (`RuntimeMemory`) нараховує й звільняє
  атомарними операціями; нарахування ніколи не виводить облік за
  необов'язкове обмеження.
- Інші потоки: потік таймерів
  ([тайм-аути receive](processes.md#receive-timeouts)), потік вводу-виводу і,
  у Windows, потік читання входу `fd` ([потік вводу-виводу](ports.md#io-thread))
  торкаються стану процесів лише через м'ютекс виконавця.
- Компонування: на Linux runtime додає `-pthread` для своїх потоків; на
  Windows він компонує Winsock (`ws2_32`, `mswsock`) для сокетів.

## Стандартний вивід

`RuntimeOptions::standard_output`
([output.hpp](../runtime/include/clause/runtime/output.hpp)) отримує вивід
`erlang:display/1` та `io` у стандартний вивід ([io](io.md)). Типова
реалізація пише в `stdout` процесу через C stdio (буферизовано); приймач хоста
повертає `false`, щоб повідомити про невдалий запис.

`erlang:display/1` відображає свій аргумент у [стилі display](terms.md#printing),
пише текст і переведення рядка одним записом і повертає `true`. Обмеження
відображення й відхилені записи стають статусами інфраструктури
(`resource_limit`, `output_failure`, ...) у перевіреному каналі, ніколи не
винятками Erlang.

## Запуск програми

`CLAUSE_main_v1` ([startup.hpp](../abi/include/clause/abi/startup.hpp),
`runtime/src/startup/`) виконує цілу програму для згенерованого `main`
([виконувані файли](executables.md)): він перевіряє ABI кожного дескриптора,
запускає runtime, реєструє всі модулі до будь-якого коду точки входу, будує
argv у контексті точки входу, виконує точку входу на виконавці й відображає
результат на [статус виходу](executables.md#exit-status). Звіти йдуть у
stderr після скидання stdout; контекст і runtime демонтуються по порядку на
кожному шляху. `CLAUSE_halt_v1` реалізує `erlang:halt/0,1` (`abort` викликає
`std::abort`).

## Відкладені служби

Вони повідомляють один рядок `[feature] notimpl` ([можливості](features.md)) і
не змінюють стану:

| Межа | Помилка |
| --- | --- |
| `TermFactory::function(FunctionIdentity)` | `TermError::not_implemented` |
| `SchedulerService::run` / `execute` | `SchedulerError::not_implemented` |
| `CodeServer::unload` | `CodeError::not_implemented` |
| `dispatch_builtin` для каталогізованої BIF | `Status::not_implemented` |

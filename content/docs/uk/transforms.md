# Parse transforms

## Використання parse transforms

- **Вимога:** на хості встановлено Erlang/OTP 29, лише для компіляції модулів,
  що використовують перетворення (transform). `clau` бере `--erl PATH`, інакше
  `erl` з `PATH`, інакше у Windows `%ProgramFiles%\Erlang OTP\bin\erl.exe`.
  `--erl none` ніколи не запускає код хоста: модулі, яким потрібне
  перетворення, не компілюються.
- **Виклик перетворення** у вихідному коді через
  `-compile({parse_transform, Module}).` (або всередині списку
  `-compile([...])`), або для кожного модуля команди через
  `--parse-transform Module` (можна повторювати; ці виконуються першими, як
  `erlc +'{parse_transform,M}'`).
- **Модулі перетворень** шукаються як файли `.beam` у каталогах
  `--transform-path` (можна повторювати) і в `transform_paths` проєкту, потім
  як `Module.erl` серед вихідних файлів пакета та `source_search_paths`
  (компілюються OTP хоста під час кожної збірки разом із модулями, які вони
  звідти викликають; діють `ignore_dirs` і `ignore_modules`),
  потім серед модулів OTP (`ms_transform`, `qlc`).
- **Попередньо компілюйте** перетворення з іншої бібліотеки (завжди) або
  перетворення проєкту, яке компілятор хоста не може зібрати з каталогами
  include і визначеннями цілі: `erlc -o deps/lib/ebin deps/lib/src/*.erl` за
  допомогою OTP хоста, потім укажіть `deps/lib/ebin` через `--transform-path`
  або в `transform_paths`. `.beam` має походити з релізу OTP хоста; `.beam`
  там має перевагу над вихідним файлом того самого модуля.
- **Що їх запускає:** компіляція, `--print-ast`, `--print-source` і
  `--print-abstr` (який показує перетворені форми); `--parse-check`,
  `--preprocess-check` і `--print-pp` — ні.

```sh
clau --erl "C:/Program Files/Erlang OTP/bin/erl.exe" --transform-path ebin -o app app.erl
```

Clause застосовує `{parse_transform, Module}` так само, як `erlc`. Він
експортує розібраний модуль як форми OTP
[abstract format](https://www.erlang.org/doc/apps/erts/absform.html),
запускає модуль перетворення на Erlang/OTP 29, встановленому на хості,
імпортує повернені форми як новий синтаксис модуля й компілює його. OTP
потрібен лише під час компіляції модуля, що використовує перетворення;
згенерованим програмам він ніколи не потрібен. Рішення ухвалено в plan step
73A; реалізовано кроками 73B–73G (`compiler/src/transforms/`).

## Поведінка OTP

За зафіксованим `lib/compiler/src/compile.erl` (`transform_module`,
`foldl_transform`, `maybe_strip_columns`) і спостереженнями під OTP 29.1.1:

- Перетворення виконуються як перший стандартний прохід: після `epp` і
  розбору, перед `erl_lint`, перед тим як `erl_internal` додає
  `module_info/0,1` і `behaviour_info/1`.
- Список перетворень — це кожен `{parse_transform, M}` з опцій компіляції
  (`erlc +'{parse_transform,m}'`), потім з атрибутів `-compile` у порядку
  форм. Перетворення, назване двічі, виконується двічі. Перед запуском
  першого ці опції видаляються з форм: атрибут `-compile`, що містить лише цю
  опцію, зникає, зі списку видаляється елемент.
- `M` має завантажуватися (`code:ensure_loaded/1`) і експортувати
  `parse_transform/2`, інакше помилка `undefined parse transform 'M'` (без
  розташування).
- `M:parse_transform(Forms, Options)` отримує форми й опції компіляції (не
  опції `-compile` з вихідного коду): `{features, Enabled}`,
  `report_warnings`, `report_errors`, `{cwd, Dir}`, `{outdir, Dir}`, `{i, Dir}`
  для кожного каталогу include, `{d, Name[, Value]}` для кожного визначення,
  а також будь-який `{parse_transform, M}`, переданий як опція.
- Вона повертає `Forms`, `{warning, Forms, Warnings}` або
  `{error, Errors, Warnings}`, де кожен список має вигляд
  `[{File, [{Location, Module, Descriptor}]}]` і форматується через
  `Module:format_error(Descriptor)`. Виняток стає помилкою
  `error in parse transform 'M': ...` (`compile:format_error/1` від
  `{parse_transform, M, {Class, Reason, Stack}}`). Наступне перетворення
  отримує форми попереднього; перша помилка зупиняє ланцюжок.
- `M:parse_transform_info/0`, що повертає `#{error_location => line}`, або
  опція компіляції `{error_location, line}` прибирає стовпці з форм перед
  запуском `M` і з остаточних форм.
- Форми мають анотації `{Line, Column}`. `epp` додає першим
  `{attribute, {1,1}, file, {File, 1}}`, те саме для кожного підключеного
  файлу на його початку, і `{attribute, {L,1}, file, {File, L}}`, коли файл,
  що підключає, продовжується з рядка `L`, наступного після його `-include`.
  Визначення макросів та інші директиви не залишають форм. Список
  закінчується `{eof, Location}` — кінцем головного файлу. Помилки
  препроцесора й розбору лишаються в списку як форми `{error, E}`, і
  `erl_lint` повідомляє про них після перетворень.
- Форми OTP 29, яких немає в `absform.md`: `{attribute, A, native_record,
  {Name, Fields}}`; імена record `{Module, Name}` (кваліфіковані) і `[]`
  (`#_`) у виразах `record`/`record_field`; `{type, A, record, [{tuple, A,
  [Module, Name]} | Fields]}` для кваліфікованих типів record; кваліфікатори
  comprehension `{zip, A, Qualifiers}`; `{mc, ...}`, `m_generate` і генератори
  `_strict`.
- `erlc +to_abstr` записує форми після перетворень (і `erl_lint`) у
  `File.abstr`, по одному терму `~p.` на форму; `erlc File.abstr`
  (`compile:file(F, [from_abstr])`) компілює такий файл без препроцесора чи
  парсера.

## Конвеєр Clause

1. Препроцесувати й розібрати модуль. Помилки препроцесора чи розбору
   зупиняють роботу тут; перетворення не виконуються для модуля з помилками
   (відмінність від OTP, який передає помилки далі як форми).
2. Зібрати перетворення в порядку OTP: опції `--parse-transform` і
   `parse_transforms` проєкту, потім атрибути `-compile`. Модуль без жодного
   пропускає решту й ніколи не запускає OTP.
3. Видалити ці опції з форм і експортувати їх: анотації `{Line, Column}` так,
   як їх призначає `erl_parse`, атрибути `file` від `epp` і `eof`. Наперед
   визначених функцій у формах ще немає.
4. Один раз запустити [завантажувач](#loader) для модуля.
5. Імпортувати повернені форми, перетворивши їх на токени, розташовані за
   їхніми анотаціями, і розібравши парсером Clause; атрибут `file` змінює
   файл наступних форм, як в `erl_lint`.
6. Додати наперед визначені функції, потім, як зазвичай, виконати lint,
   аналіз і компіляцію.

Перетворення виконуються під час компіляції модуля і для `--print-ast`,
`--print-source` і `--print-abstr`, які друкують перетворений модуль.
`--preprocess-check`, `--parse-check` і `--print-pp` їх не запускають.

## Обмін даними

- `clau` і завантажувач обмінюються файлами External Term Format
  (`term_to_binary`, версія 131, без стиснення): точні float, атоми UTF-8,
  великі цілі числа й жодного розбору тексту в Erlang. Сам формат (теги,
  розміщення, перевірки меж) описано один раз в
  `abi/include/clause/abi/external_term.hpp`, незалежно від будь-якого
  представлення термів, тож майбутні `term_to_binary/1`, `binary_to_term/1`
  і дистрибуція в runtime використають його повторно.
  Модель термів компілятора Clause містить атоми,
  цілі числа, float, правильні й неправильні списки, кортежі, map і
  bitstring; pid, порти, посилання й fun відхиляються з діагностикою.
- Текст `.abstr` має синтаксис [`file:consult/1`](https://www.erlang.org/doc/apps/kernel/file.html#consult/1):
  один терм на форму, кожен закінчується `.`. `--print-abstr` друкує форми
  кожного модуля після перетворень у цьому синтаксисі в stdout, по одній формі
  на рядок; вхідний файл `.abstr` компілюється як `erlc File.abstr`. Clause
  записує канонічний текст, а не розкладку `~p` з OTP; важить рівність термів.
  Форми дорівнюють `epp:parse_file(F, [{location, {1, 1}}])` для кожної
  конструкції з `tests/fixtures/transforms/abstract/`, включно з атрибутами
  `file` від `epp` (явний `-file` анотується як
  `[{generated, true}, {location, L}]`) і `eof`, відрахованим від останнього
  `-file` головного файлу.

## Імпорт форм

Повернені форми та вхідні файли `.abstr` (позиційні або `sources` проєкту)
стають токенами, розташованими за їхніми анотаціями, і проходять через парсер
Clause, тож отримують ті самі синтаксичні перевірки, що й вихідний код;
пріоритет операторів визначає, де додаються дужки. Приймаються
`{Line, Column}`, просто `Line` (показується як `file:line:`) і списки
властивостей із `location` і `file`; `generated` ігнорується. Атрибут file
змінює файл наступних форм; якщо цей файл існує, імпортований код зберігає
свої налагоджувальні рядки й коментарі з вихідним кодом. Некоректні форми є
помилками в місці їхньої анотації (`unknown expression bogus`,
`expected {Name, Arity}`, `invalid annotation`), і модуль не компілюється;
форми OTP `{error, _}`/`{warning, _}` повідомляються з їхнім дескриптором,
для форматування якого потрібен OTP. Імпорт експортованого модуля й повторний
експорт дають ті самі форми.

## OTP хоста

- `erl` шукається в такому порядку: `--erl PATH`, `erl` з `PATH`, потім у
  Windows `%ProgramFiles%\Erlang OTP\bin\erl.exe`. Якщо його не знайдено, коли
  модулю потрібне перетворення, це помилка з назвою перетворення й модуля;
  запасного варіанта, що пропускає перетворення, немає.
- Хост має працювати на OTP 29 (`erlang:system_info(otp_release)`); інший
  реліз — помилка.
- [Завантажувач](#loader) запускається як `erl -noshell -noinput -pa Dir ... -eval ...`
  (каталоги шляху коду перетворено на абсолютні) з обмеженням часу 600 с. Його
  stdout і stderr (включно з виводом `io:format` перетворення) копіюються в
  stderr `clau` після його завершення.
  Завантажувач, що завершується без запису відповіді, перевищує час або не
  може запуститися, — це помилка.
- Перетворення виконує довільний код із правами користувача, точно так само,
  як під `erlc`.

## Завантажувач

`compiler/src/transforms/loader/clause_transform_loader.erl` належить проєкту
і вбудований у `clau`. Кожен запуск записує його й запит у новий тимчасовий
каталог, `clause-transform-*` у `<build_dir>/tmp`
([каталог збірки](projects.md#build-directory)) або, для позиційних вхідних
файлів без `--build-dir`, у системний тимчасовий каталог, який видаляється
після запуску; `erl` компілює й завантажує завантажувач у пам'яті. Запит
містить форми, опції, список перетворень, ім'я файлу модуля і вихідні файли
перетворень проєкту, які треба зібрати. З каталогом збірки відповідь і вивід
завантажувача зберігаються в [кеші збірки](projects.md#build-caches) й
використовуються повторно, поки запит і все, від чого він залежить, не
змінюються; список sticky-модулів хоста зберігається так само. Завантажувач:

1. перевіряє реліз OTP;
2. компілює запитані вихідні файли перетворень проєкту в пам'яті й
   завантажує їх;
3. для кожного перетворення: завантажує його, прибирає стовпці, як просить
   `parse_transform_info/0`, викликає `parse_transform/2` і форматує
   попередження й помилки в `{File, Location, Text}` через
   `Module:format_error/1`;
4. записує `{ok, Forms, Warnings}` або `{error, Errors, Warnings}` і
   зупиняється.

## Модулі перетворень

Модуль перетворення шукається в такому порядку:

1. **Попередньо скомпільовані файли `.beam`** у каталогах `--transform-path DIR`
   (можна повторювати) і опції проєкту `transform_paths`, які потрапляють у
   шлях коду завантажувача перед каталогами OTP. Це єдиний спосіб використати
   перетворення з бібліотеки-залежності: спершу зберіть цю бібліотеку за
   допомогою OTP хоста (наприклад, `erlc -o deps/lib/ebin deps/lib/src/*.erl`);
   Clause ніколи не збирає залежності. `.beam` має походити з того самого
   мажорного релізу OTP, що й хост.
2. **Вихідні файли поточного проєкту**: `Module.erl` у пакеті або в його
   `source_search_paths`, який завантажувач компілює в пам'яті з каталогами
   include і визначеннями цілі під час кожного запуску, разом із модулями
   проєкту, які він викликає за іменем (знайденими так само). Пошук
   пропускає вихідні файли, які виключають `ignore_dirs` або `ignore_modules`,
   як це робить [пошук модулів](projects.md#ignored-sources). Clause шукає ці
   вихідні файли один раз на пакет і тримає їх у пам'яті; завантажувач однаково
   компілює їх для кожного модуля, до якого застосовується перетворення, тож
   велике перетворення варто попередньо скомпілювати, щоб заощадити цей час.
   Модулі, які хост завантажує зі своїх sticky-каталогів (`kernel`, `stdlib`,
   `compiler`, як-от `ms_transform` чи `qlc_pt`, коли вихідні файли OTP є в
   шляху пошуку), не можна перезавантажити, тому використовуються власні
   модулі хоста: їхні вихідні файли й модулі, які викликають лише вони, не
   шукаються й не компілюються.
   Clause запитує в `erl` хоста ці модулі один раз за виклик.
3. **Власні модулі OTP** (`ms_transform`, `qlc`) зі шляху коду хоста.
   OTP постачає `erl_id_trans` лише як приклад вихідного коду, а не як модуль.
   Їхні заголовки розв'язуються так само, як кожен `include_lib`
   ([препроцесор](preprocessor.md#compatibility-policies)): зіставте
   застосунок, як у
   `--app-dir "stdlib=C:/Program Files/Erlang OTP/lib/stdlib-8.1"` для
   `include_lib("stdlib/include/ms_transform.hrl")`, або назвіть перетворення
   напряму через `-compile({parse_transform, ms_transform})`.

Компіляція перетворення проєкту може завершитися невдачею там, де його
справжня збірка вдається: заголовки залежностей, перетворення самого
перетворення або макроси, які визначає лише інший інструмент збірки. Тоді
Clause виводить повідомлення компілятора щодо вихідного файлу перетворення
з підказкою попередньо скомпілювати його в `.beam` за допомогою OTP хоста й
передати його каталог через `--transform-path`. Перетворення проєкту також
компілюється Clause як звичайний модуль, коли воно входить до пакета; тоді
його власним викликам (`erl_syntax`, `erl_parse`, ...) можуть знадобитися
бібліотечні модулі, яких Clause не постачає, тож не додавайте перетворення до
`sources` цілі, якщо вони потрібні лише перетворенню.

## Діагностика

| Ситуація | Повідомлення |
| --- | --- |
| Немає OTP на хості | `File: parse transform 'M' needs Erlang/OTP 29 on the host; pass --erl` |
| `--erl` не вказує на виконуваний файл | `File: erl not found: PATH` |
| Неправильний реліз OTP | `parse transforms need Erlang/OTP 29 on the host, found N` |
| Перетворення не знайдено | `File: undefined parse transform 'M'` (текст OTP) |
| Перетворення згенерувало виняток | `File: error in parse transform 'M': ...` (текст OTP) |
| Попередження чи помилка перетворення | `File:Line:Column: Text` як повернуто |
| Вихідний файл перетворення не компілюється | його повідомлення, потім підказка про попередню компіляцію |
| Шлях перетворень не існує | `File: parse transform path is not a directory: DIR` |
| `.beam` у шляху перетворень не завантажується | `File: cannot load parse transform 'M' from PATH: Reason` |
| Завантажувач збоїв, перевищив час або не записав відповіді | `parse transform loader failed: ...` |
| Некоректні повернені форми | діагностика парсера в місці форми |

## Опції

| CLI | Проєкт (`[targets.options]`) | Значення |
| --- | --- | --- |
| `--parse-transform M` | `parse_transforms = ["m"]` | Застосувати `M` до кожного модуля перед його власними перетвореннями з `-compile` (спершу ті, що з CLI) |
| `--transform-path DIR` | `transform_paths = ["deps/*/ebin"]` | Шлях коду для попередньо скомпільованих файлів `.beam` перетворень; шаблони як у `source_search_paths` |
| `--erl PATH` або `none` | — | Виконуваний файл `erl` хоста; `none` ніколи не запускає код хоста |
| `--print-abstr` | — | Надрукувати форми після перетворень замість компіляції |

Проєкт, що використовує власне перетворення і попередньо скомпільоване з
залежності:

```toml
[[targets]]
name = "app"
sources = ["src/*.erl"]

[targets.options]
source_search_paths = ["transforms"]  # transforms/pt_rewrite.erl, compiled for each build
parse_transforms = ["pt_dep"]         # applied to every module of the target
transform_paths = ["deps/*/ebin"]     # deps/ptdep/ebin/pt_dep.beam, built with erlc first
```

Не додавайте модулі перетворень до `sources` цілі, якщо програма їх не
викликає: як звичайні модулі вони теж компілювалися б Clause, а їхні виклики
`erl_parse` чи `erl_syntax` потребують модулів, яких Clause не постачає.
